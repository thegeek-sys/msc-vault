## Assembler basics
In order to understand concepts of system security we need some x86/x64 assembler basics. It is necessary to understand what a given binary executable does. We will use **reverse engineering** as technique to help us.

	// sum numbers from 1 to 42

## Compiler
![[Pasted image 20261031162520.png|447]]

The phases from top to bottom:
1. `Program → Abstract Syntax Tree`. The frontend reads the source code and converts it into a tree that represents its structure.
2. `AST → High-Level IR`. The tree is translated into a first intermediate representation; still quite similar to the starting language
3. `High-Level IR → Low-Level IR`. The representation becomes more and more similar to machine code
4. `Low-Level IR → Machine code`. The last step of code generation that produces instruction for a specific CPU (e.g. x86-64)

>[!info] Intermediate Representation
>**IR (Intermediate Representation)** is a form of the program that sits between your source code and the final machine code. It’s not C, and it’s not x86 assembly. It’s a simplified, regular, machine-independent language that the compiler uses internally.
>
>Why compilers need it
>1. **It avoids an explosion of translators.** Say you have 3 languages (C, Rust, Swift) and 3 CPUs (x86-64, ARM64, RISC-V). Without an IR you’d need 3 × 3 = 9 separate compilers. With an IR, each language only translates _to_ the IR (3 front ends), and each CPU only translates _from_ the IR (3 back ends). That’s the design of LLVM, the dragon on slides 15-17. The example on slides 26-30, where the same `testFunc` is shown for x86, x86-64, ARM64 and RISC-V, comes from exactly this setup.
>2. **It’s a good place to optimize.** Source code is full of syntax and quirks, and machine code is full of CPU-specific details. An IR is simple and uniform, so optimizations like inlining, loop unrolling, dead code removal and constant folding can be written once and work for every language and every CPU. This is the “…” between High-Level IR and Low-Level IR on slide 17: many passes that gradually make the code simpler and closer to the machine.
>3. **It’s gradual.** High-Level IR still has structures like loops and arrays. Low-Level IR is close to “do this operation, store in this register”, which makes the final step to machine code easy.

### Basic terms
A program consists of several **procedures** (or functions) and procedures consists of several **basic blocks**. The basic blocks are the “atomic” units of a program, the maximal sequence of consecutive instruction with two properties:
- flow of control only enters at the beginning
- flow of control can only leave at the end

>[!example]- Basic block
>```asm
>B1:  1189  endbr64
>     118d  push rbp
>     118e  mov  rbp, rsp
>     1191  mov  [rbp-0x8], 0x0     ; j = 0
>     1198  mov  [rbp-0x4], 0x1     ; i = 1
>     119f  jmp  11ab               ; salta al controllo
>
>B2:  11a1  mov  eax, [rbp-0x4]     ; <-- destinazione di jle
>     11a4  add  [rbp-0x8], eax     ; j += i
>     11a7  add  [rbp-0x4], 0x1     ; i++
>
>B3:  11ab  cmp  [rbp-0x4], 0x2a    ; <-- destinazione di jmp
>     11af  jle  11a1               ; se i <= 42, torna a B2
>
>B4:  11b1  mov  eax, [rbp-0x8]     ; dopo jle
>     11b4  pop  rbp
>     11b5  ret
>```

### Generated code
When translating a program, compilers often add their own piece of code which has no correspondence in high-level representation, for example:
- start-up code to include libraries/initialize runtime
- code to save processor registers before jumping to subroutine
- characteristic traces left by compiler (e.g. specific translation of code constructs)

In addition compilers can also remove specific information during compilation phase (e.g. optimization like loop unrolling or inlining).

>[!tldr] Binary code looks quite different compared to source code

For all these reasons, the analysis process cannot be completely automated. You need to carefully review analysis results generated by a tool (and maybe correct mistakes).

### Obfuscation
Code can be made intentionally more complex than it should be in order to hide semantic from human analysts and to complicate reverse engineering (e.g. DRM application).

Commonly malware use *packers* to obfuscate the code. The actual malware is the packed payload which at the beginning contains a small stub at the beginning to decode it. The binary only exist at runtime, when the stub is done working and actual code is in memory.

## Machine language
**Machine code** is a sequence of elementary machine instructions on which the CPU directly works on. The **machine language** is the textual representation of this machine code.

The set of all machine instruction is called **instruction set architecture** (*ISA*), and each architecture has its own machine language ad distinct byte patterns (x86 vs. Intel/AMD)

### Assembler
Machine code is (almost) unreadable for humans as it’s only made up of bit sequences (e.g. `10110000`). For this reason **assembler** gives mnemonic names for each valid bit sequence (e.g. `mov al, 61h` where `h` stands for hexadecimal).

The assembler code can be easily understood by humans and is translated (almost) directly into machine code (can present small differences between assembler and machine code)

>[!example]
>```c
>int testFunc(int* input, int length) {
>	int sum = 0;
>	for (int i = 0; i < length; i++) {
>		sum += input[i];
>	}
>	return sum;
>}
>```
>
>Intel x86-64
>```nasm
>testFunc(int*, int):
>    ; --- prologue: set up the stack frame ---
>    push rbp                        ; save caller's base pointer
>    mov  rbp, rsp                   ; rbp = start of this function's frame
>	
>    ; --- spill arguments to the stack (unoptimized code does this) ---
>    mov  qword ptr [rbp - 8], rdi   ; input  = 1st arg (rdi), pointer -> 8 bytes
>    mov  dword ptr [rbp - 12], esi  ; length = 2nd arg (esi), int     -> 4 bytes
>	
>    ; --- local variables ---
>    mov  dword ptr [rbp - 16], 0    ; sum = 0
>    mov  dword ptr [rbp - 20], 0    ; i = 0
>
>.LBB0_1:                            ; loop header (condition check)
>    mov  eax, dword ptr [rbp - 20]  ; eax = i
>    cmp  eax, dword ptr [rbp - 12]  ; compare i with length
>    jge  .LBB0_4                    ; if i >= length, leave the loop
>	
>    ; --- body: load input[i] ---
>    mov  rax, qword ptr [rbp - 8]       ; rax = input (base address)
>    movsxd rcx, dword ptr [rbp - 20]    ; rcx = i, sign-extended to 64 bit
>    mov  edx, dword ptr [rax + 4*rcx]   ; edx = *(input + 4*i) = input[i]
>    ; [...]
>```
>
>Intel x86
>```nasm
>testFunc(int*, int): # @testFunction(int*, int)
>	push ebp
>	mov ebp, esp
>	sub esp, 8
>	mov eax, dword ptr [ebp + 12]
>	mov ecx, dword ptr [ebp + 8]
>	mov dword ptr [ebp - 4], 0
>	mov dword ptr [ebp - 8], 0
>.LBB0_1: # => Inner Loop Header: Depth=1
>	mov eax, dword ptr [ebp - 8]
>	cmp eax, dword ptr [ebp + 12]
>	jge .LBB0_4
>	mov eax, dword ptr [ebp + 8]
>	mov ecx, dword ptr [ebp - 8]
>	; [...]
>```
>
>ARM64
>```nasm
>testFunc(int*, int):
>	mov x4, x0
>	cmp w1, 0
>	ble .L4
>	mov x2, 0
>	mov w0, 0
>.L3:
>	ldr w3, [x4, x2, lsl 2]
>	add w0, w0, w3
>	add x2, x2, 1
>	cmp w1, w2
>	bgt .L3
>.L1:
>	ret
>; [...]
>```
>
>RISC-V
>```nasm
>testFunc(int*, int): # @testFunction(int*, int)
>	addi a2, zero, 1
>	blt a1, a2, .LBB0_4
>	mv a2, zero
>.LBB0_2: # =>This Inner Loop Header: Depth=1
>	lw a3, 0(a0)
>	add a2, a2, a3
>	addi a1, a1, -1
>	addi a0, a0, 4
>	bnez a1, .LBB0_2
>	add a0, zero, a2
>	ret
>.LBB0_4:
>	mv a2, zero
>; [...]
>```

#### Bytecode
Interpreted languages (e.g., Python or Java) are translated into **bytecode** which is then executed by an interpreter, making assembler code different from bytecode. Furthermore there are many optimizations possible, e.g. Just-In-Time (JIT) compiler or ahead-of-time (AOT) compiler

## Intel x86/x64 Architecture
The **x86** family is based on the **8086** (1978), whose success was due to the IBM PC. It has been continuously developed: 286, 386, Pentium, Core, Ryzen, etc.

- **IA-32**: the 32-bit architecture, since the **386** (1985)
- **x86-64** (*AMD64* / *Intel 64*): the 64-bit extension (introduced by AMD in 2003)
	- today's default and our focus
	- IA-32 programs still run on it
	- **not** IA-64 (aka *Itanium*), which is a different, discontinued ISA

>[!warning] Naming
>Colloquially, "x86" often means 32-bit (IA-32) and "x64" means 64-bit (x86-64).

### Architecture specifics
- **64-bit** architecture: registers and pointers are 64 bits wide, but 32-bit programs still run
- **CISC** CPU (*Complex Instruction Set Computer*): many, complex instructions. The opposite is **RISC** (ARM64, RISC-V): few, simple instructions
	- x86-64 has **16** general-purpose registers (IA-32: only **8**), plus many special-purpose ones
	- instructions are **1-15 bytes** long. `push rbp` is 1 byte (`55`), `mov dword ptr [rbp-0x8], 0x0` is 7 bytes. In RISC they all have the same size
	- in practice the CISC/RISC line has blurred: internally the CPU translates each instruction into simple RISC-like **micro-operations**
- rather expressive and complex memory management

>[!example] CISC vs RISC
>x86 can do arithmetic directly on memory in one instruction, ARM64 has to load first:
>```nasm
>add dword ptr [rbp-0x8], eax   ; x86: read memory, add, write back
>
>ldr w3, [x4, x2, lsl 2]        ; ARM64: load into a register...
>add w0, w0, w3                 ; ...then compute on registers
>```

## x86/64 registers
Memory access on (almost) all CPU architectures goes through registers for performance reasons (registers are fast as they are places inside the CPU) and they can be accessed similarly to variables.

Their size depends on the architecture: **64 bits** on x86-64, **32 bits** on IA-32

### Important x86-64 registers
Registers are small, fast storage units inside the CPU. There are **general purpose** and **special purpose** registers. Many more exist (FPU, SSE, ...) but they are not interesting for us.
#### General purpose registers
| x86-64     | IA-32 | Typical purpose                         |
| ---------- | ----- | --------------------------------------- |
| `rax`      | `eax` | Accumulator; holds the **return value** |
| `rbx`      | `ebx` | Base address for addressing             |
| `rcx`      | `ecx` | Counter for loops, index                |
| `rdx`      | `edx` | Data; upper half for `mul` / `div`      |
| `rsi`      | `esi` | Memory address for string source        |
| `rdi`      | `edi` | Memory address for string destination   |
| `r8`-`r15` | -     | General use (x86-64 only)               |

>[!warning] Only a convention
>Compilers use these registers freely, but some instructions insist on specific ones, e.g. `loop` counts down `rcx`.

#### Special purpose registers
| x86-64   | IA-32    | Typical purpose                                                                                   |
| -------- | -------- | ------------------------------------------------------------------------------------------------- |
| `rsp`    | `esp`    | Stack pointer: points to the last pushed stack element (**decreases**, the stack grows downwards) |
| `rbp`    | `ebp`    | Base pointer: points to the current stack frame (by convention)                                   |
| `rip`    | `eip`    | Instruction pointer: points to the next instruction to be executed                                |
| `rflags` | `eflags` | Status flags, typically used for conditional jumps and to indicate certain situations             |

- `rip` / `eip` is also called **program counter** (`pc`)
- `rip` and the flags can only be written and read **indirectly**, you cannot `mov` into them

>[!example] Indirect access
>`cmp` sets the flags and `jge` reads them. `jmp`, `call` and `ret` change `rip`.
>```nasm
>cmp eax, dword ptr [rbp - 12]   ; sets rflags
>jge .LBB0_4                     ; reads rflags, may change rip
>```

### Subregisters
x86-64 has **16** general-purpose registers, each **64 bits** wide (IA-32: 8 of 32 bits). The lower 32, 16 and 8 bits of each can also be addressed on their own. For the new registers the suffixes are `d`, `w`, `b`: `r8d`, `r8w`, `r8b`. Subregisters exist for backward compatibility with 8/16/32-bit programs.

![[Pasted image 20261031183417.png]]

![[Pasted image 20261031183153.png]]
(same for `rbx`/`rcx`/`rdx`)


>[!warning] Write rules
>- writing an **8- or 16-bit** part does **not** change the other bits
>- writing a **32-bit** part **zeroes** bits 63-32

>[!example] Subregisters
>```nasm
>mov rax, 0x1122334455667788   ; rax = 11223344 55667788
>mov al,  0xff                 ; rax = 11223344 556677ff (last 2)
>mov ax,  0xbeef               ; rax = 11223344 5566beef (last 4)
>mov eax, 0x12345678           ; rax = 00000000 12345678  <- upper half zeroed
>```

### Data sizes
| Name                  | Size              | Register part | Typical C type   |
| --------------------- | ----------------- | ------------- | ---------------- |
| **BYTE**              | 8 bits = 1 byte   | `al`          | `char`           |
| **WORD**              | 16 bits = 2 bytes | `ax`          | `short`          |
| **DWORD** (double word) | 32 bits = 4 bytes | `eax`       | `int`            |
| **QWORD** (quad word) | 64 bits = 8 bytes | `rax`         | `long`, pointers |

- the name gives you the access size: `mov dword ptr [rbp-0x8], 0` writes **4 bytes**
- gdb has its own unit names: `x/w` means 4 bytes

>[!warning] A WORD is 16 bits, even on x86-64

### Other registers
- **x87** floating point: register stack `st0` ... `st7` (80 bit)
- **MMX**: `mm0` ... `mm7` (64 bit)
- **SSE/AVX**: `xmm0` ... `xmm15` (128 bit), `ymm` (256), `zmm` (512)
- **Segment registers**: `fs` / `gs` point to thread-local data
- **Control registers**
	- MMU controls (`cr3`: page tables)
	- debugging (`dr0` - `dr7`)
	- model-specific registers (MSRs)
- many more are documented in the Intel manuals

### Disassembler
Turns bytes into instructions. Each line of the output has: address, raw bytes, instruction.
```nasm
1189:  f3 0f 1e fa           endbr64
118d:  55                    push rbp
118e:  48 89 e5              mov  rbp,rsp
1191:  c7 45 f8 00 00 00 00  mov  DWORD PTR [rbp-0x8],0x0
```
More advanced disassemblers exist (e.g. IDA, see the graph view).

### ELF header
| Field                   | Meaning                                                    |
| ----------------------- | ---------------------------------------------------------- |
| **Magic** `7f 45 4c 46` | `\x7f E L F`, how `file` recognizes the format             |
| **Class**               | ELF64 or ELF32                                             |
| Data                    | 2's complement, little endian                              |
| Type                    | `DYN` = Position-Independent Executable (PIE)              |
| Machine                 | x86-64                                                     |
| **Entry point**         | address of the first instruction, `_start` (e.g. `0x10a0`) |

### ELF sections
![[Pasted image 20261031185424.png]]

| Section | Holds | Flags |
| ------- | ----- | ----- |
| `.text` | instructions | `AX`: in memory, executable |
| `.rodata` | constants, e.g. string literals | `A`: in memory, read-only |
| `.data` | initialized global variables | `WA`: in memory, writable |
| `.bss` | zero-initialized global variables | `WA`, **no bytes in the file** (`NOBITS`) |

`readelf` = header and sections, `objdump` = the instructions.

### How a debugger works
**Mechanism on Linux**
- `ptrace`: the kernel stops the process for the debugger
- **Breakpoint**: one code byte is replaced by `int3` (`0xcc`)
- **Single step**: uses the **trap flag** in `rflags`

**What we can do with it**
- stop at an instruction
- execute one instruction at a time
- inspect registers and memory
- change them

>[!warning] Observing is not free
>The run is slower and the program can notice it.
